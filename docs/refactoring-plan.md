# Novel Auto Generator 重构与可靠性改进方案

制定日期：2026-09-30。代码基线：`c333ca2`，插件版本：`1.8.1`。

状态：已开始实施，具体结果见 [执行记录](progress.md)。未勾选的任务及目标接口仍为规划。

## 1. 目标与范围

本次采用渐进重构：先在现有结构中修复可靠性问题，再按业务边界迁移，最后清理兼容代码和完善工程约束。保留已有效工作的解析、合并、历史、分类及导出逻辑，并用回归测试保护。

最终应达到以下结果：

- 用户能准确知道任务在运行、等待、暂停、失败还是完成；任务不会无限等待，不会将失败或残缺响应显示为成功。
- 停止、重新开始、切换聊天、重新打开界面后，旧任务不能污染新任务。
- 刷新、任务完成、存储失败后，已确认保存的数据仍可恢复；旧任务文件和世界书仍可使用。
- 开发者能从界面动作直接定位业务操作、数据写入和外部调用，减少多层转发。
- 核心业务可以在没有 SillyTavern 和 DOM 的环境中测试；宿主兼容通过独立适配层及集成测试验证。
- 安装仍使用 SillyTavern 的扩展安装方式，用户不需要运行 npm 或自行构建。

本轮保留两大业务：自动续写小说、TXT 转世界书。世界书现有串行/独立并行/分批并行、分卷、分类、提示词消息链、修复、重 Roll、合并、历史、导入导出均进入回归范围。

本轮不引入后端服务、云同步、团队协作或新的模型供应商；不全量更换 UI 框架、不同时重写提示词语义与数据模型。多任务列表等产品扩展后置，先把当前任务保存可靠。

## 3. 技术决策

| 决策       | 方案                                                                           |
| ---------- | ------------------------------------------------------------------------------ |
| 重构方式   | 每次迁移一条业务路径；可独立测试、独立回退，不一次搬完目录                     |
| 运行技术   | 保持原生 ESM 和现有 DOM/jQuery；业务不依赖 jQuery，UI 可继续使用               |
| 类型检查   | 先对新增契约和迁移模块使用 JSDoc + `checkJs`；不要求一次性转换全部代码         |
| TypeScript | 完整迁移作为后续选项；若采用，必须另行解决构建产物与扩展更新分发，不让用户编译 |
| 状态管理   | 小型显式任务控制器与按业务划分的数据对象，不引入大型状态框架或通用事件总线     |
| 模型请求   | 供应商适配、传输、业务重试各有边界；同一逻辑操作共享总尝试预算                 |
| 数据       | 先保持现有世界书结构，附加 ID 与配置元数据；不在目录迁移时顺带改变全部字段     |
| 宿主支持   | 以能力检测和验证过的版本矩阵为依据，不只依据 README 的 “1.10+” 声明            |
| 性能       | 先测量长文本、快照和大列表开销；保留 100 MB 文件上限，未验证前不提高上限       |
| 发布       | 根入口、manifest、全局 API 和安装方式保持稳定；不在本方案中预定版本号          |

依赖规则：

1. UI 调用 commands 并订阅进度/结果；commands 调用处理、格式、请求和仓储。纯算法层不访问 DOM、酒馆全局或存储。
2. `host/` 是唯一直接读取酒馆全局和导入酒馆绝对路径模块的生产代码位置。旧路径过渡期例外必须列在迁移清单中。
3. `shared/` 不反向导入 `novel/` 或 `worldbook/`；仅真正共用的能力进入 shared。
4. 业务操作接收必要的接口，例如模型客户端、任务仓储和进度回调；不传入整个应用对象来隐藏依赖。
5. `bootstrap` 只创建对象和连接依赖，不处理业务。每个业务模块可以有一个局部装配函数，不再增加多层同义转发。
6. 占位 noop 不作为缺失依赖的正常兜底。必需依赖缺失应在初始化时明确失败，可选能力使用显式判断。
7. 旧全局 API 的兼容行为集中处理；内部代码迁移后不再直接调用 `window.TxtToWorldbook`。

发布用 JavaScript 保持浏览器可直接加载，不引入需要打包器解析的裸模块路径。开发工具依赖只用于检查与测试；真正需要运行时依赖时先确定其浏览器分发方式。

## 5. 任务生命周期和并发契约

### 5.1 状态与操作

任务状态统一为 `idle / running / pausing / paused / stopping / stopped / completed / failed`。`repair`、`reroll` 是操作类型，不再与生命周期混为布尔标志。UI 所需的 `isRunning` 等值从状态计算。

| 操作 / 事件 | 状态变化                                    | 必须遵守的行为                                                               |
| ----------- | ------------------------------------------- | ---------------------------------------------------------------------------- |
| 开始        | idle/stopped/completed/failed → running     | 同一任务只允许一个控制器运行；失败重试保留已提交结果                         |
| 暂停        | running → pausing → paused                  | 停止派发新块，等待已发块完成或到达时限；成功结果保存后才显示已暂停           |
| 恢复        | paused → running                            | 创建新的 runId，从未提交成功的块继续                                         |
| 停止        | running/pausing/paused → stopping → stopped | 立即撤销旧运行提交资格，取消可取消请求、等待清理；保留已提交成果             |
| 调度结束    | running → completed                         | 所有计划项都有确定结果；用 outcome 区分全部成功、含失败、含跳过              |
| 致命故障    | 活动状态 → failed                           | 配置、授权、存储等错误停止派发，展示原因及恢复方式                           |
| 关闭主弹窗  | 调用暂停流程                                | 默认保存后隐藏，保留现有“关闭会停止工作”的使用预期；后台运行作为后续独立选项 |
| 切换聊天    | 续写任务暂停或停止                          | 立即禁止向新聊天发送，不仅依赖提示用户                                       |

开始、暂停、恢复、停止必须幂等；UI 禁用按钮之外，command 层也必须拒绝非法状态转换。

### 5.2 运行上下文

每次运行持有：`taskId`、唯一 `runId`、任务配置快照、AbortController、资源清理集合、并发队列和当前数据 revision。续写额外持有宿主聊天标识；无法可靠识别聊天时，开始前明确要求选择并绑定。

- 所有请求回调、计时器和存储提交携带 runId。写入时校验活动运行、任务、revision，旧回调最多记录被丢弃，不更新 UI 或数据。
- 更换任务时串行交接控制器，不复用旧信号量、控制器或可变的全局停止标记。
- 配置默认在开始时快照；运行中修改默认设置只影响下次运行，避免同一任务中途改变模型、分类或合并策略。
- 未完成的流式文本仅作预览；解析、验证和事务提交全部成功后才标记块成功。
- `finally` 清理计时器、监听器、reader、并发许可；旧运行的 finally 也不得重置新运行的状态。

### 5.3 三种处理策略与重生成

- 串行：前一块提交成功后构造下一块上下文。
- 独立并行：请求不依赖实时变化的生成结果；使用启动时明确的上下文快照，按原始顺序提交结果。
- 分批并行：每批共享同一世界书摘要，上一批完成提交后更新下一批摘要。
- 队列块拥有稳定 ID、父块 ID、来源位置及显示顺序；Token 超限分裂后保留来源关系，不再把数组索引当身份。
- 一个块的同一次尝试只能提交一次；恢复重放不能重复追加内容。
- 重 Roll 使用新的 attemptId；成功后替换该块的有效结果，再按规则重建受影响条目。保留人工编辑层与来源记录，不用粗暴全量重建覆盖人工修改。
- 同一世界书运行转换时，不允许另一项合并/修复/重 Roll 同时写入；界面和 command 双重检查。

### 5.4 自动续写的特殊处理

发送聊天消息不是天然可重复的操作。超时后先确认本次用户消息和 AI 消息是否已存在，不能直接再次点击发送。

为每次续写记录起始楼层、用户消息标识、AI 消息标识、发送与生成结果。无法判断发送是否成功时进入待处理的暂停状态，让用户选择继续等待或重新尝试，不自动制造重复消息。

优先订阅验证过的宿主生成状态/事件；DOM 轮询只作兼容回退。回退模式设置开始等待、内容等待和整轮总时限，识别生成按钮状态，并保留通知弹窗的有界等待。不能仅凭字符数短暂不变认定成功。

## 6. 请求、错误与响应校验

### 6.1 模型客户端契约

各供应商提供一致的生成入口，接收 messages、模型配置、signal、时限与进度回调；返回文本、结束原因、是否完整、供应商元数据和可获得的用量。

能力声明包含：消息角色支持、流式支持、取消支持、模型列表支持、并发上限。酒馆宿主能力在已验证前按单并发处理；自定义 API 沿用用户设置并发值并做范围校验。

OpenAI-compatible、Gemini、Anthropic 分别维护请求/响应映射；模型测试必须调用对应适配器。无模型列表能力时允许手动填写，并明确提示，不向错误接口发请求。

酒馆字符串回退可能改变角色语义或注入预设内容，继续保留兼容说明。版本/能力检测失败不触发另一条无界重试链。

对无法确认取消成功的宿主请求，超时不代表上游已经结束。此时暂停新请求，等待宿主完成信号或用户处理宿主状态；不能因本地 Promise 超时就释放宿主调用资格并立即重试。界面仍可停止本地任务和丢弃旧结果，但不得声称已取消上游生成。

### 6.2 错误模型与预算

- 统一 `code / httpStatus / retryable / cause / provider`；错误文案只用于展示，兼容识别集中到一个入口。
- 用户取消不可重试；401/403 和明确配置错误停止任务；网络错误、超时、408/429/可重试 5xx 按策略退避。
- Token 上限作为明确的拆块/减小输出策略，不能把所有 `INVALID_ARGUMENT` 都直接视作 Token 上限。
- 建议默认一个块最多发出 4 次模型请求，其中最多 1 次用于内容修复；全部请求共享计数，修复也消耗预算。
- 网络退避与内容修复分开决策，共用取消信号和预算；支持有上限的 Retry-After 与随机抖动。
- 拆块额外设置最大深度、最小块长和任务累计请求预算，防止递归分裂形成请求风暴。

### 6.3 流与内容

请求开始、总时限、流空闲时限分别管理，总时限覆盖响应体读取。异常断流、主动取消、空闲超时和正常完成有不同结果。兼容现有 apiTimeout 字段时通过迁移映射提供明确默认值。

SSE 解析需覆盖 CRLF、跨包分行、UTF-8 多字节拆包、合法的 `data:` 格式、心跳、错误事件、结束标记和结束原因；释放 reader lock。结束原因表示长度截断时，即使 JSON 可解析也不算成功。

只有已验证的供应商可使用“正常 EOF 即完成”的兼容策略；其余缺失结束证据的响应作为不完整结果处理。保留残片供本地诊断或用户查看，但不进入世界书提交路径。

JSON 容错之后还必须经过结构校验。针对新生成条目要求有效名称和非空正文；关键词缺失时按明确规则补条目名。增量更新可以采用部分字段，但必须针对已存在条目产生有效变化。空对象、错误页和代理排队文本不属于有效更新。校验策略变化需增加旧样本与误拒绝样本测试。

## 7. 数据、恢复与格式迁移

### 7.1 数据职责

将“默认设置”“任务创建时配置”“运行瞬态”“结果与历史”“凭据”分开保存。暂停和恢复使用任务配置，不取当前表单或后来修改的全局设置。

建议的数据对象如下，首轮通过 JSDoc 定义和运行时校验约束：

| 对象        | 关键字段                                                                                           |
| ----------- | -------------------------------------------------------------------------------------------------- |
| Task        | schemaVersion、taskId、kind、sourceIdentity、configSnapshot、status、outcome、revision、时间与计数 |
| Chunk       | chunkId、parentId、sourceRange、order、status、attemptId、error、resultRevision                    |
| Entry       | entryId、分类/名称、关键词/内容、entryConfig、sourceChunkIds、updatedRevision                      |
| History     | historyId、taskId、revision、操作、受影响条目、变更前后值或检查点                                  |
| Credentials | provider、endpoint 关联标识和密钥；不复制进任务快照及普通导出                                      |

现有 `{分类: {条目名: {关键词, 内容}}}` 在迁移初期保持可用，稳定 ID、来源和配置可以先作为并行元数据保存。改名、跨分类移动和别名合并必须更新关联关系。

### 7.2 提交与恢复

- 为同一 taskId 串行提交块结果，在同一 IndexedDB 事务中更新有效结果、世界书变更、历史及任务进度；Promise 在事务 `oncomplete` 后成功。
- 网络请求、解析和大计算必须在事务外完成，防止事务被浏览器提前关闭。
- 使用 operationId/attemptId 去重和 revision 检查；事务失败不显示成功，不继续推进依赖该结果的块。
- 定期检查点只是补充，主要依靠块级提交。完成任务保留最终结果，清理是显式操作。
- 页面退出、后台挂起只能尽力保存；恢复时将 `running/processing` 等瞬态归一为可继续状态，已提交块保持成功。
- 存储配额不足或被禁用时暂停任务，提供导出当前内存结果的恢复路径，不静默覆盖旧检查点。
- 多标签页对同一任务只允许一个写入者。优先使用可用的浏览器锁，并以事务内所有者/租约/revision 校验兜底；后台挂起后失去租约的实例必须停止提交。

### 7.3 旧数据迁移与回退

首轮采用“保留旧库，新任务库迁移”的方案，避免直接升级原数据库后旧插件因版本下降无法打开。

1. 包装旧 `TxtToWorldbookDB` v7 的读取接口，准备匿名化旧任务、分卷、Roll 历史和配置 fixtures。
2. 新建任务数据库，例如 `TxtToWorldbookTasks` v1，在同一新库内完成新数据的跨表事务；数据库名属于实现常量，不暴露给业务。
3. 从旧库读取，校验并复制到新库；保留旧数据，不在读取期间清理历史。旧文件中 `version: 2.9.0` 按历史格式识别，不当作插件版本。
4. 对每批迁移记录来源和完成标记；只有目标数据事务完成且数量/内容校验通过，才切换活动指针。重复执行迁移不得产生重复条目。
5. 一个 taskId 只有一个活动写入后端；不长期双写新旧库，也不声称两个数据库之间可以原子提交。
6. 旧续写进度没有可靠聊天标识时，先保留为未绑定旧任务，由用户确认目标聊天后恢复，不能自动绑定当前聊天。
7. 新版本回退时，旧库是迁移时的基线，不包含新进度。回退前将新成果导出为兼容格式；无法无损表示的新元数据另外保留完整备份，并说明限制。
8. 原库删除不属于本轮自动迁移，稳定后再提供用户可控制的清理功能。

### 7.4 世界书与公开 API 兼容

- 世界书导入同时接受 entries 数组、entries 对象和现有内部格式；字段类型在入口校验。
- 保存并恢复禁用、蓝绿灯、位置、深度、顺序、关键词、递归等已支持参数；未知字段作为导入元数据保留，导出时由显式编辑覆盖对应字段。
- 角色卡格式、分卷文件、完整任务文件各用独立版本/转换函数；不把内部分卷 JSON 当成 ST 世界书格式宣传。
- 普通任务/设置导出默认不含凭据；需要携带凭据时提供单独的显式选项。旧文件仍能导入，密钥迁入凭据存储。浏览器本地存储不等于加密保险箱，不使用同处保存的密钥作无意义加密。
- 保留 `window.TxtToWorldbook` 的方法、别名、返回形状和现有 getter 的可变引用行为；不能在小版本中偷偷改为冻结对象或深拷贝。
- 新内部代码全部使用 commands；旧 API 直接修改返回对象的行为属于兼容例外，通过契约测试记录。未来若要改成只读快照，需要独立的 API 版本和弃用期。
- 保留 `initTxtToWorldbookBridge/getTxtToWorldbookApi`、`nagDebug` 和既有主要 DOM id，直到确认无依赖或提供迁移说明。

## 8. 界面与可观测性

本轮界面工作围绕运行行为，先保持现有入口和主要布局。

- 进度分别显示待处理、运行、成功、失败、跳过；结束时明确是否有失败项。
- 等待中显示原因和已等待时间，例如模型响应、重试退避、暂停收尾、保存结果。
- 暂停、停止、恢复和重试可用性从任务状态派生；恢复不会偷偷修改当前模型设置。
- “读取原文”“AI 结果”“最终世界书”分清来源；流式预览不标为已保存成果。
- 主弹窗、子弹窗的打开/关闭使用统一生命周期，重复打开不会重复绑定事件。
- 样式提取时保持宿主主题变量、移动端底部操作区、滚动与触摸行为；中文默认及已存在的英文翻译保持可用。
- 日志包含 taskId、runId、chunkId、attempt、provider、耗时、错误码，默认不输出密钥、完整正文或带凭据 URL。
- 调试日志采用有上限的本地缓冲；诊断导出脱敏，不新增远程遥测。

## 11. 测试策略与验收矩阵

保留已有 182 项测试的有效断言，不为得到新目录而批量重写测试。先按实际需求增加 fixtures 和测试层级，再移动既有测试。

| 层级 / 场景 | 覆盖点                                               | 实现方式                                                |
| ----------- | ---------------------------------------------------- | ------------------------------------------------------- |
| 纯函数      | 标签过滤、切块、Prompt、解析、合并、字段映射         | Vitest；固定输入与预期语义                              |
| 请求层      | 供应商请求头/消息、SSE、结束原因、错误码             | 本地假响应/可控流；不调用付费模型                       |
| 调度层      | 并发上限、乱序完成、暂停、旧运行、预算耗尽           | 可控 Promise、假计时器、真实调度器                      |
| 存储集成    | 原子提交、去重、revision、迁移、事务失败             | fake-indexeddb 加故障注入；关键路径再跑浏览器 IndexedDB |
| 完整业务    | 导入→提取→校验→合并→保存→重开→导出                   | 只替换模型/宿主外部边界，使用真实解析、合并、仓储实现   |
| 故障恢复    | 事务前/中/后中断、配额不足、标签页竞争               | 检查持久化结果及重放幂等，不仅检查函数被调用            |
| 格式兼容    | ST 数组/对象 entries、旧任务、分卷、角色卡、未知字段 | 匿名 fixture 与字段级往返比较                           |
| 宿主交互    | 加载、发送、生成完成、切换聊天、按钮状态             | 浏览器模拟宿主契约 + 固定版本真实酒馆 smoke             |
| 界面回归    | 反复开关、窗口高度、触摸滚动、翻译                   | 浏览器测试和人工核对；沿用原 17 项回归并补续写场景      |
| 长任务      | 1 MB/10 MB 文本、较大条目集、长时间任务              | 固定机器/浏览器记录峰值内存、耗时、渲染次数及持久化耗时 |

首批必须具备的故障回归：

1. 429 和超时可重试，401 与用户取消不重试，嵌套调用不突破总预算。
2. 流返回部分正文后停滞，任务失败且世界书不变。
3. 模型返回空对象、错误页或长度截断，不能标记块成功。
4. 停止后马上启动，旧响应、旧计时器和旧 finally 均不能修改新任务。
5. 暂停后不派发新块，已发块收尾保存；恢复不重复处理已提交成功块。
6. 续写发送结果不确定时不自动重复发送；切换聊天后不再向新聊天写入。
7. 事务写入失败时不推进进度；重新加载后结果与历史一致。
8. 完成任务刷新后可恢复成果；人工编辑在重 Roll/重建后按既定规则保留。

支持矩阵在 B00 固定：当前主力酒馆版本、一个仍承诺支持的较旧版本；Chromium 和 Firefox 的关键流程；移动端至少验证操作区和滚动。版本号、系统、浏览器及是否真实模型必须记录。模拟宿主通过不能替代真实宿主验收。

## 13. 发布、回退与提交规范

- 第一轮修复可以独立发布；任务模型和存储切换分别发布，避免一次更新跨越所有兼容边界。
- 保持根入口和 manifest 的资源路径；新增模块随仓库发布并校验相对 import，禁止发布只存在于开发机的文件。
- 代码迁移、行为修复、格式清理尽量分开，PR 描述写清触发条件、前后行为、验证和迁移影响。
- 若使用分支，默认 `codex/` 前缀，例如 `codex/api-reliability`；每批提交前更新 CHANGELOG。
- commit 使用约定式提交和中文描述，例如 `fix(api): 修复流式响应超时后误判成功`、`refactor(tasks): 统一任务生命周期与运行隔离`。
- 如需依赖 GitHub，网络失败时可以使用本机 7897 代理，代理配置不写入仓库。
- 首轮重构保留旧数据读取能力和旧 API 入口，切换路径应有明确检查点；不长期维护两套同时工作的业务引擎。
- 回退演练必须覆盖“新版本已处理新内容”的情形，不能只证明旧代码能启动。通过完整备份和兼容导出保护新成果，再回退代码。

发布完成标准：所有必需检查通过、真实宿主关键流程通过、旧样本可恢复、普通导出无凭据、完成成果刷新后存在、断流和停止竞态不污染数据、安装更新和回退说明准确。
